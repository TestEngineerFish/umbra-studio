# 24 · 从外部打开文件：右键「打开方式」· 拖拽 · 命令行

**这份只管这一件事**：怎么让 Umbra Studio 能被别的地方「叫起来打开某个文件 / 目录」。
需求出处仍是 `doc/01`（打开一个目录）；排期进 `doc/12`。

起因：用户 2026-10-20 提的 —— 打完包之后「只能在项目中查看对应目录的文件」，
希望 ① Finder / 资源管理器右键「打开方式」里能选它 ② 能把文件拖进来自动打开。
他点名让我看看 Typora / Sublime Text 怎么做。**他明确要求先调研。**

⚠️ 本文读数全是 2026-10-20 在本机实测（读源码 / 读已装应用的 `Info.plist` / 读
`app-builder-lib` 的 schema 与实现），标〔判断〕的才是我的意见。

## 〇、先说结论

| # | 结论 |
| --- | --- |
| 1 | **技术上全都能做，而且我们已经有一半** —— `open-dir` 这条宿主事件通道早就通了（壳发 → preload 桥 → `App.tsx` 听） |
| 2 | **难的不是技术，是概念**：「打开方式」给的是**一个单文件**，而我们的模型是**一个目录**。单文件的「项目根」是什么，必须先定 |
| 3 | ⚠️ **最大的风险是会往用户目录里写东西** —— `open_project` 第一次打开会调 `buildIndex`，它在**项目根写 `index-data.js`**、建 `.umbrastudio/`、拷运行时。右键打开 `~/下载/某.md` 就会在**下载文件夹里拉一摊文件** |
| 4 | Typora 已经示范了我们要的那条声明：`public.folder` + `LSHandlerRank = Alternate`（**能接文件夹，但不抢默认**） |

## 一、我们现在的实际状态（实测）

| 查的 | 读数 |
| --- | --- |
| `fileAssociations`（electron-builder） | **没有** → **Finder 的「打开方式」里压根不会出现 Umbra Studio** |
| `mac.extendInfo` / `protocols` | **都没有** |
| `app.on("open-file")`（macOS 用它打开文件的事件） | **没监听** |
| `second-instance` | 在，但**只 focus 窗口，把 argv 扔了** —— Windows 上「用它打开」第二次启动时文件路径就在 argv 里 |
| 首次启动的 `process.argv` | 只用来判 `--mcp`，**没取文件路径** |
| 拖拽 | 应用侧没有 drop 处理 |

**已经有的那一半**（这是好消息）：

```
shell/main.mjs   sendHost({ type: "open-dir", dir })     ← 菜单「打开目录…」与「最近打开」在用
shell/preload.cjs  ipcRenderer.on("host:event") → onEvent
app/src/host/types.ts  HostEvent = { type: "open-dir"; dir } | …
app/src/App.tsx   onEvent 里收 open-dir → inspect_dir → 是项目就 open，否则进「新建」面板
```

所以**加一条 `open-file` 事件是顺着现成的路走**，不是新开一条。

**另一个有利前提**：`buildProject(dir)` **不要求 `project.json`** ——
`readConfig(dir) ?? { name: 目录名 }`。所以**任意目录都能当项目**，
单文件的父目录天然可以做项目根。

## 二、别人怎么做（读本机已装应用的 `Info.plist`，不是凭记忆）

### 2.1 三种策略，差别很大

| 应用 | `CFBundleDocumentTypes` 条数 | 策略 |
| --- | --- | --- |
| **Typora** | **3** | Markdown（`Owner`）+ Plain Text（`Alternate`）+ **Folder（`Alternate`）** |
| **Sublime Text** | **5** | 少数几条 + 一条老式通配兜底（`CFBundleTypeOSTypes = ****`），`Alternate` |
| **Cursor** | **66** | 一种语言一条，**全是 `Owner`** |

### 2.2 Typora 那三条的原文（最值得抄的）

```
① Markdown    LSItemContentTypes = io.typora.markdown, net.daringfireball.markdown
              CFBundleTypeExtensions = md markdown mmd mdown mkd … （13 个）
              CFBundleTypeRole = Editor      LSHandlerRank = Owner      ← 抢默认
② Plain Text  CFBundleTypeExtensions = txt text
              LSItemContentTypes 里含 public.data
              CFBundleTypeRole = Editor      LSHandlerRank = Alternate  ← 能开，不抢
③ Folder      LSItemContentTypes = public.folder
              CFBundleTypeRole = Viewer      LSHandlerRank = Alternate  ← **我们要的就是这条**
```

**`LSHandlerRank` 是这件事唯一真正重要的旋钮**：

| 值 | 意思 |
| --- | --- |
| `Owner` | 我是这类文件的主人 —— **抢默认**（双击就用我打开） |
| `Alternate` | 我能开 —— **出现在「打开方式」里，但不抢默认** |
| `Default` / `None` | electron-builder 的缺省是 `Default` |

⚠️ **Cursor 那 66 条全 `Owner` 对我们是反面教材**：装完它之后一堆文件的默认打开方式被换掉，
是很多人抱怨过的事。我们是个**目录工作台**，不是某种格式的主人 ——
**除了 `.dc.html` 之外都该是 `Alternate`**。

〔判断〕`.dc.html` 可以是 `Owner`：那是我们自己的格式，没有别人会抢。

### 2.3 它们的产品模型（这比机制重要）

| | 模型 | 单文件打开之后 |
| --- | --- | --- |
| **Typora** | **文档为中心**，一个窗口一个文档 | 就显示那一个文档；侧边栏可以另外开一个「文件树」目录 |
| **Sublime Text** | 文件 + 文件夹都行 | 开一个**没有项目的窗口**，只有那个文件；之后可以再 Add Folder |
| **Cursor / VS Code** | **文件夹为中心**，但允许「没有文件夹的窗口」 | 单文件窗口，很多功能（搜索、Git、任务）**明说要先打开文件夹** |

**我们最像 VS Code 那一类**（目录为中心、很多能力绑在项目上：索引、快照、评论、点选地址、AI 上下文）。
而 VS Code 的答案是：**允许单文件窗口，但老实承认它功能不全，并引导你打开文件夹。**
〔判断〕这条路对我们是对的 —— 比「悄悄把父目录接管成项目」诚实得多（见 §三）。

## 三、⚠️ 真正的坑：打开就会往人家目录里写东西

这是本次调研**最该带走的一条**，它不是机制问题，是后果问题。

`api.ts` 的 `open_project` 里：

```ts
const s = await serveStart(target);
if (!s.indexExists) await buildIndex(target, s.url);   // ← 第一次打开就跑
```

而 `buildIndex`（`indexpage.ts`）会往**项目目录**写：

| 写什么 | 在哪 |
| --- | --- |
| `.umbrastudio/` 目录 + 索引数据 | 项目根下 |
| **`index-data.js`** | **项目根**（`writeAtomic(join(p.dir, "index-data.js"), …)`） |
| 点选桥 `select-bridge.js` | 项目根的 `.umbradesign/` |
| tokens 副本 | 子目录 |

**所以「右键用 Umbra Studio 打开 `~/下载/某.md`」的后果是：在用户的下载文件夹里拉出一摊文件。**

⚠️ 这件事和纪律⑥ 是同一条的延伸：
纪律⑥ 说的是「**我们**不往 `projects/` 里留东西」，
而这一次是「**产品**会往用户随手打开的任何目录里留东西」—— 后者更严重，因为用户没同意。

反过来说，好消息有两条：
- `buildProject()` / `migrateUdDir()` **都不主动建目录**（只在旧目录存在时拷）；
- `.umbrastudio/` 下的东西（快照 / 体检 / 评论）是**第一次写的时候**才建的，不是打开时。

**所以写盘的触发点只有一个：`buildIndex`。** 这让「只看不写」成为一个**可以做到**的档位。

## 四、可行性与做法（技术部分，都有出处）

### 4.1 macOS：声明「我能打开什么」

`electron-builder` 的 `fileAssociations` 支持的字段（读 `app-builder-lib/scheme.json`）：

```
ext · name · description · icon · isPackage · mimeType · role · rank
rank: "Owner" | "Default" | "Alternate" | "None"   （缺省 Default，对应 LSHandlerRank）
```

⚠️ **它只认扩展名，没有 `LSItemContentTypes`** → **声明不了 `public.folder`**。

**但可以合并**（读 `app-builder-lib/out/electron/electronMac.js:179`，注释是它自己写的）：

```js
// `CFBundleDocumentTypes` may be defined in `mac.extendInfo`, so we need to merge it in that case
appPlist.CFBundleDocumentTypes = [...(appPlist.CFBundleDocumentTypes || []), ...documentTypes];
```

**是合并不是覆盖** → 做法定了：

| 要声明的 | 用什么 |
| --- | --- |
| 扩展名那些（`.dc.html` / `.md` / `.json` / 代码 / 图片…） | `fileAssociations`，`rank: "Alternate"`（`.dc.html` 可以 `Owner`） |
| **文件夹** | `mac.extendInfo.CFBundleDocumentTypes` 加一条 `public.folder` + `Viewer` + `Alternate`（照 Typora ③） |

### 4.2 macOS：接住那个事件

`app.on("open-file", (e, path) => …)`。

⚠️ **它可能在 `app.whenReady()` 之前就触发** —— 所以必须在**模块顶层**就注册，
把路径先攒进一个队列，窗口好了再发。这是这类实现最常见的漏法：
注册在 ready 之后 → **冷启动（应用没开着时右键打开）那一下丢掉**，
而**热启动（应用已经开着）却正常** —— 于是「有时候行有时候不行」。

### 4.3 Windows：两条路，都要接

| 情形 | 路径在哪 |
| --- | --- |
| 应用没开着，右键打开 | **首次启动的 `process.argv`** |
| 应用已开着，右键打开 | 第二个进程启动 → single-instance 把它挤掉 → **`second-instance` 回调的 `argv`** |

⚠️ 我们现在 `app.on("second-instance", () => { … focus … })` —— **参数都没接**。
这是 Windows 上「打开方式点了没反应」的现成原因。

⚠️ 还要防「把别的参数当文件」：`--mcp` 这类开关、还有 Windows 传进来的
可能是**带引号的路径**。做法：只取**存在于磁盘上的绝对路径**，其余忽略。

### 4.4 拖拽：有个版本陷阱

实测本机 `shell/node_modules/electron` = **44.4.5**。

⚠️ **Electron 32 起 `File.path` 被移除了** —— 老教程里的
`e.dataTransfer.files[0].path` 在我们这个版本上是 `undefined`。
正确写法是 `webUtils.getPathForFile(file)`（实测 `electron.d.ts` 里有 `webUtils` 与 `getPathForFile`）。
而我们 `contextIsolation: true`，所以**要在 preload 里包一层**经 `contextBridge` 暴露。

⚠️ 另外拖拽有两个落点，别只做一个：
- **拖到窗口里**（renderer 的 `drop`）
- **拖到 Dock / 任务栏图标上** —— macOS 那条走的还是 `open-file`

### 4.5 命令行（顺带，几乎零成本）

`umbra <路径>` 这件事在 4.3 做完之后基本白送（首次启动读 argv 那一支）。
〔判断〕值得同时做，因为它是**唯一能写进判据的那条路** ——
右键菜单与拖拽都要真人操作或驱动系统 UI，而命令行可以在 `shelltest` 里直接验。

## 五、要定的那件事：单文件打开之后，项目根是什么

**这是本文唯一需要你拍板的问题**，三条路：

| 路 | 做法 | 好处 | 代价 |
| --- | --- | --- | --- |
| **(a) 父目录接管成项目** | 打开 `~/下载/某.md` → 把 `~/下载` 当项目打开，选中那个文件 | 一步到位，所有能力都在 | ⚠️ **会往 `~/下载` 写 `index-data.js` 与 `.umbrastudio/`**（§三）—— 用户没同意 |
| **(b) 先只看，写盘前再问**〔推荐〕 | 同样以父目录为根，但**跳过 `buildIndex`**、进「只看」档：能看、能圈给 AI、**不写一个字节**；需要落盘 / 体检 / 评论时才弹一次「要把这个目录接管为项目吗？（会在这里建 `.umbrastudio/`）」 | 诚实、零污染、能力随用户同意逐步解锁 | 要给「只看」档一条明确的界面说法（VS Code 那种「打开文件夹以启用 X」） |
| **(c) 只接文件夹，不接单文件** | 「打开方式」只声明 `public.folder` | 最小、最保守 | 用户要的正是**单文件**那一下，等于没解决 |

〔判断〕**(b)**。理由两条：
① §三 那摊文件是真会发生的，而**「悄悄在用户目录里建东西」属于那种装一次就被卸掉的行为**；
② 我们已经有「不画假的、明说还没做」的先例（M11-6 不画假余额）——
「只看档 + 明说缺什么」和那条是同一个取向。

⚠️ 还有一个附带问题要一起定：**打开之后是新窗口还是换当前窗口？**
我们现在是**单窗口 + single-instance**。VS Code / Sublime 是多窗口。
〔判断〕第一期**换当前窗口**（最小改动），但要处理「当前有没落盘的改动」——
那道闸（`askLeave`）已经有了，接上就行。

## 六、顺带发现的两条

1. **`inspect_dir` 与「任意目录都能当项目」口径不一致**：
   `App.tsx` 走 `inspect_dir` 判 `isProject`，不是项目就进「新建」面板接管；
   而 `buildProject` 本身不要求 `project.json`。
   〔判断〕(b) 那条路正好把这件事理顺：**「是项目」= 已经有 `.umbrastudio/`；
   没有的就是「只看」**，而不是弹一个「新建项目」面板打断人。

2. **`second-instance` 丢 argv 这件事现在就是个缺陷**，不只是新功能的前置 ——
   Windows 上任何「第二次用它打开」的场景都已经失效，只是至今没人走到。

## 八、用户 2026-10-20 的更正：旁数据一律进我们自己的目录

他的原话（要点）：**无论临时打开文件还是导入文件夹，都不应该在用户的那个目录里新增任何东西**；
要新增的（项目配置、文件历史…）**统一放在我们项目自己指定的资源地址**，
每导入一条就在那里新建一个文件夹，装这条记录除文件本身以外的一切；
最近历史也从我们自己的配置地址读；指向的东西不在了要提示（最好实时）；
目标没了我们的配置也不必留 —— **删最近记录 / 清除本地缓存时一起清掉**；
而**清除缓存这个功能现在没有，要补一个**。

### 8.1 这个更正我接受，而且它比我 §五 提的方案更彻底

我 §五 推的是 (b)「先只看，**写盘前再问**」—— 那还是承认了「迟早要往用户目录写」。
他要的是**根本不写**。两条理由让我认为他的更对：

- **「问一次」解决不了问题，只是把污染推迟了。** 用户点一次「接管」，`~/下载` 里照样多出一摊东西；
- **旁数据今天本来就不共享**（见 8.3）—— 放在用户目录里换不来任何好处。

### 8.3 为什么「搬走」不损失东西 —— 它今天本来就不共享

租户模板 `doc/_模板-租户 .gitignore` 的第一条就是：

```
# 工具产物：快照、体检记录、缩略图、索引缓存。可由稿件重算 / 重体检，不必进仓库。
.umbrastudio/
.umbradesign/
```

所以 ⓐⓑ **默认就被 git 忽略**，跟项目走也拷不给同事。
（模板留了一句「若希望语义 diff 的历史随仓库一起走，把这行注释掉」——
那是个 opt-in，不是默认。）

实测体积也不是问题：`projects/Umbra_design/.umbrastudio` = **452 KB**，整个项目 10 MB。

⚠️ **但模板那句注释有一处不准确，而它正好决定「清缓存」能清什么**：
「可由稿件重算」对 ⓑ（checks / shots / index）成立，
**对 ⓐ 不成立** —— 快照是**过去的内容**，算不出来；评论、回收站、模板同理。
**这条区分是 8.6 那条安全线的全部依据。**

### 8.4 唯一真正的冲突：`./support.js` 是相对引用

实测一份真稿（`projects/Umbra_design/经营账本 · 第一批.dc.html`）：

```html
<script src="./support.js">            ← 相对引用
<link href="umbra-ink-tokens.css">
<link href="_ds/umbra-design-system-…/styles.css">
<script src="_ds/umbra-design-system-…/_ds_bundle.js">
```

而 `support.js` / `react*.production.min.js` **就躺在那份稿旁边**。
这不是实现偷懒，是 `doc/01` 与 CLAUDE.md §1 那句产品定位：
**「一份文件同时是设计稿、规范出处和可运行原型」** ——
双击那个 `.dc.html`，它要能自己跑起来，不依赖我们的应用。
纪律① 也是为它存在的（「绕过写入口写出来的页会因为缺 `__resources` 而在断网时白屏」）。

**好消息是：这条冲突和你要解决的场景不重叠。**

| 场景 | 要不要 ⓒ |
| --- | --- |
| **临时打开一个 `.md` / 一张图 / 一个任意文件夹** | **完全不要** —— 看 Markdown 不需要 `support.js` |
| 临时打开一份**别人的 `.dc.html`** | **也不要** —— 我们已经有一条**不落盘的预览路**：`/__preview/` 在响应里注入点选桥，而 `apitest` 有一条判据钉着「**盘上那份没被动过**（注入只发生在预览这条路上）」 |
| 你**自己的设计项目**，要那份稿能独立跑 / 能交给别人 | **要**，而这正是今天的行为 |

〔判断〕所以结论是**按「这个目录是什么」分档，而不是在旁数据上妥协**：

- **临时 / 只看档**：ⓐⓑ 全进 `STATE_ROOT`，ⓒⓓ **一个字节都不写** —— 你要的那条，完全成立；
- **我的设计项目档**（用户显式说「这是我的 Umbra 项目」）：ⓒ 照旧落在项目里
  （否则 `.dc.html` 不再是可运行原型），而 ⓐⓑ 也进 `STATE_ROOT`。

### 8.5 ⚠️ 两条现成缺陷，正好挡在这件事路上

**① `exists` 判的是 `project.json`，不是目录本身。**

```ts
// server/src/workspace.ts:81
.map((r) => ({ ...r, exists: existsSync(join(r.dir, "project.json")) }));
```

后果两条，第二条是致命的：
- 今天：一个**任意目录**（没有 `project.json`）被打开过 → 最近列表里**永远显示成「不存在」**，哪怕目录好好的；
- 按新架构：**我们不再往用户目录写 `project.json`** → **所有记录都会显示成「不存在」**。

所以 `exists` 必须改成判**目录本身**（`existsSync(r.dir)`），
而「这条是不是我们接管过的项目」改成**看 `STATE_ROOT` 里有没有那条记录**。
**这件事不做，8.4 那一档一上线就全线报错。**

**② 真的没有「清除缓存」。** 现有的只有
`purge_trash`（回收站单项）· `clear_staged_draft` · `clear_recent_projects`（清**列表**，不清缓存）。
你说得对，要补。

### 8.6 设计：`STATE_ROOT` 下按记录一个文件夹

```
STATE_ROOT/.umbrastudio/
├── workspace.json          ← 最近打开（已有）
└── records/
    └── <key>/
        ├── record.json     ← 指向哪个目录 / 显示名 / 最后打开 / 是不是「接管的项目」
        ├── snapshots/      ← ⓐ 不可重算
        ├── comments.json   ← ⓐ
        ├── trash/          ← ⓐ
        ├── templates/      ← ⓐ
        ├── checks/         ← ⓑ 可重算
        ├── shots/          ← ⓑ
        └── index/          ← ⓑ（含原来写在项目根的 index-data）
```

**`<key>` 怎么取**〔判断〕：`sha256(realpath(dir))` 前 16 位。
- 好处：查找零成本，不用先读一张索引表；
- ⚠️ **必须 `realpath`** —— macOS 上 `/var` 是指向 `/private/var` 的链接，
  不解的话**同一个目录会产生两条记录**。这个坑我们自己踩过
  （`verbtest` 那条「临时目录要 `realpath`，否则沙箱按真路径放行会 import 不到」）；
- 代价：用户把目录**移走**之后记录就孤立了 —— 第一期靠「清除缓存」收尾，不做重绑。

### 8.7 ⚠️ 「清除缓存」的安全线：它绝不能把文件历史带走

这是本节最要紧的一条。按 8.2 的分类，`records/<key>/` 里**同时**装着
「可重算的缓存」和「**算不出来的用户资产**」。
如果「清除缓存」= 删掉那个文件夹，那么用户点一下就**永久丢掉所有版本历史与评论**，
而他以为自己只是清了缓存。

所以「清除缓存」要分三档，**而且默认那一档不碰 ⓐ**：

| 档 | 清什么 | 说法 |
| --- | --- | --- |
| **① 清缓存**（默认） | 只清 ⓑ：`checks/` · `shots/` · `index/` | 「重体检一次就回来」 |
| **② 清掉已失效的记录** | 目标目录**已经不在**的整条记录（含 ⓐ） | 对应你说的「目标没了我们的配置也没必要留」 |
| **③ 删掉这一条记录** | 某一条的整个文件夹（含 ⓐ） | **要说清「版本历史也会删掉」并让他确认** |

⚠️ 而「从最近列表去掉一项」**不该**连带删 ⓐ ——
那是两个动作（「我不想在列表里看到它」≠「我要丢掉它的历史」）。
〔判断〕去掉列表项时问一句「顺便把它的历史也删掉吗？」，默认**不删**。

### 8.8 「实时提示目标不在了」

你说「如果能做到实时当然最好」。实测：

- **打开那一刻判** —— 零成本，`existsSync` 一下（修完 8.5① 就对了）；
- **列表上实时** —— `list_recent_projects` 已经每次都 `existsSync`，所以**打开首页那一刻就是最新的**；
- **开着的时候目标被删** —— 要 watcher。我们已经有磁盘监听（M11-5 修过它硬编码扩展名那条），
  〔判断〕第一期**不新开 watcher**：目标目录消失时现有监听会报错，接住它提示一次就够。

## 十、什么时候才建目录（用户 2026-10-20 第二轮补充）

他的补充：**不该每次打开就建一个文件夹** —— 真实使用会非常频繁地打开和关闭，
所以打开应该只落在「记录」里，**有编辑操作之后**再往统一配置里建东西。

**按「第一次产生了什么」决定什么时候建**，分三层：

| 层 | 放哪 | 什么时候建 | 清掉的代价 |
| --- | --- | --- | --- |
| **打开记录** | `workspace.json` 里**一行** | 每次打开 —— **零目录** | 无 |
| **缓存** | `cache/<key>/` | 第一次体检 / 第一次要缩略图 / 第一次建索引 | 重算一次就有 |
| **资产** | `records/<key>/` | **第一次产生算不出来的东西**：第一次落盘（→快照）· 第一次评论 · 第一次暂存 · 第一次进回收站 | **删了就没了** |

**资产目录的创建触发点是可枚举的四个**，不是一句模糊的「有编辑」。

两个顺带的好处：
- **「是不是我们接管过的项目」第一次有了客观判据** = `records/<key>/` 在不在 ——
  不用再看 `project.json`（正好修掉 §8.5① 那条缺陷）；
- 打开 = 零目录，意味着 **`buildIndex` 必须从 `open_project` 里挪成按需** —— 这是具体要改的那一处。

实测两个支撑点：
- 最近列表**写入时就封顶**（`workspace.ts` 的 `MAX_RECENT = 20`）→ 频繁打开不会让它无限长；
- 快照**已经有大小上限**（`recordCreatedFile`：超过设置里的二进制上限、默认 100 MB 就不存，回一句原因）。

## 十一、git 的分工与大文件（用户 2026-10-20 问的）

他的问题：以前不用 git 是怕和用户项目自带的 git 冲突；现在既然我们与用户目录无侵入了，
**用 git 管版本是不是更好？大文件会不会有问题？**

### 11.1 他想的那个架构**已经在跑**

`gitkeep.ts:157` 起：

```
GIT_DIR       = STATE_ROOT/.umbrastudio/git/<名字>__<路径哈希>    ← 我们的目录，bare
GIT_WORK_TREE = 用户的项目目录
忽略规则       → <GIT_DIR>/info/exclude，**不碰项目的 .gitignore**
```

**分离式 git：用户目录里一个 `.git` 都不建。** 他当初那个顾虑在 M9-7（2026-09-28）就按这个思路解掉了。

所以问题不是「能不能用 git」，而是**要不要把它从「兜底」升级成「主路径」（替掉 `.src.gz` 快照）**。

### 11.2 ✅ 已定：**不升级**。理由是一条 git 给不了的性质 —— 按条删

| | 我们的快照 | git |
| --- | --- | --- |
| 文本省空间 | 每版整份 gzip | **明显更省**（delta + pack） |
| **二进制**省空间 | 整份 gzip | **差不多** —— pack 的 delta 对已压缩的 png/jpg 几乎无效 |
| **能删掉单个历史版本吗** | **能**（就是一个文件） | **不能** —— 要 `filter-repo` 重写历史，`gc` 只清不可达对象 |
| 捕获「别的编辑器改的那一版」 | **不能**（只在走写入口时产生） | **能** ← 它存在的全部理由 |
| 语义分级 diff（L1–L4） | 有 | 没有，只有字节 diff |

而「**按条删**」正是 §十 那个「清除缓存 / 目标没了就清」的前提。
**git 做不到「只清这一个文件的历史」** —— 一个 500 MB 的 psd 进过历史就永远在 pack 里。

**结论：分工不变、各补对方盲区。** git 当兜底（捕获外部修改），快照当主路径（可按条删 + 语义分级）。

### 11.3 大文件：实测 + 一个现成的缺口

- 实测 `.umbrastudio/git` = **93 MB / 591 个仓库**，而排序出来是
  `umbrastudio-filetest-*`(265) · `新项目`(111) · `evil`(61) · `gitfallback`(28) ——
  **基本全是回归残留**（这是「清掉自己造的状态」的**第四处**，§166 那三处的同族）。
  真实项目很小：`Umbra_design` 的兜底仓库只有 **80 KB**；
- 快照那边**有**上限（`recordCreatedFile`，默认 100 MB）；
- ⚠️ **git 那一侧没有上限** —— `gitkeep.ts` 里只有 `maxBuffer`（那是子进程输出缓冲，不是文件大小）。
  它的注释写着「git 那一版同理不记」，**而代码里没有这道闸**。注释又一次比代码乐观。

## 十二、身份：怎么知道「还是那个文件夹」（用户 2026-10-20 第三轮）

他的场景：关联桌面的 `A` → 删掉 → **新建一个同名 `A`** → 旧记录还在吗？会不会冲突？
是不是不该只用绝对路径、要不要加 hash 或创建时间？

### 12.1 今天的行为（实测）：比「冲突」糟 —— 是**静默继承**

键在三处**都是纯路径**：

| 在哪 | 键 |
| --- | --- |
| `records/<key>/`（§8.6 提的） | `sha256(realpath(dir))` |
| 兜底 git 仓库 | `<目录名>__<路径哈希>` |
| `workspace.json` 最近列表 | `r.dir === dir` **字符串相等**（`workspace.ts:51`） |

所以那个场景的结果是：

1. 删掉 A → 记录**还在**（没人清）；列表会标「不存在」—— ⚠️ 而今天 `exists` 判的是
   `<dir>/project.json`，所以这个标记本来就不准（§8.5①）；
2. 新建同名 A → **键完全相同** → **静默继承**旧 A 的快照 / 评论 / 回收站；
3. 再次导入 → **不报冲突，直接认成同一个**。

**这比冲突糟**：冲突会提示，而静默继承让用户看到一份从不属于这个文件夹的版本历史，
甚至可能「回退」到一份陌生的内容。

### 12.2 为什么不能简单加 inode 或创建时间

**本机 APFS 实测**：

| 操作 | inode | birthtime |
| --- | --- | --- |
| 删掉再新建同名 | **变了** ✅ 判得出来 | **变了** ✅ |
| 改名 `A`→`B` | **没变** ✅ 身份能跟着走 | 没变 |

**但跨平台查证下来，每个信号都有坑**（出处见 §12.5）：

| 信号 | 坑 |
| --- | --- |
| Windows 的 file ID | 官方说明是**可能被复用** |
| **创建时间** | ⚠️ Windows 的**文件系统隧道（tunneling）**会让同名新建的文件**继承旧文件的创建时间** —— 这条直接毁掉「用创建时间当判据」 |
| `st_dev` | Linux 上**跨重启不保证稳定**（异步设备枚举） |
| `st_ino` on Windows | 网络盘上不可靠；ReFS 上 64 位 ID 不唯一，要 128 位 `FILE_ID_INFO` |

**macOS 的标准答案（security-scoped bookmark）我们用不了**：
实测 Electron 的 `securityScopedBookmarks` 标着 `_mas_`
（`electron.d.ts:23222`：「Create security scoped bookmarks **when packaged for the Mac App Store**」），
而我们是直接下载分发。

**别人怎么做**：VS Code 就是**路径哈希 + 从不清理**，社区得自己写 `vscode-workspace-gc`
去删「路径已不存在」的条目 —— 主流编辑器是带着这个问题在跑的。

### 12.3 ✅ 已定的做法：换目标 —— 不求「鉴定」，只求「不许静默继承」

**这个转换是本节的全部**：我们不需要内核级的身份判定，只需要**错的时候用户看得见**。

> **不可靠的信号用来「报警」是安全的，用来「认人」才危险。**

记录里存一份**指纹** `{ dir, dev, ino, birthtimeMs, firstSeenAt }`，打开时比对：

| 比对结果 | 怎么做 |
| --- | --- |
| 路径在、指纹**全对** | 就是它，正常打开 |
| 路径在、指纹**不对** | **判为「这个位置换了一个」** —— **不继承**，问一句「要把旧记录（含历史）当成它的吗？还是新建一条？」 |
| 路径在、**指纹缺失**（老条目 / 平台取不到） | **当「未知」，不报警**（向后兼容；报警会让所有老条目全线弹窗） |
| 路径**不在** | 标「已删除」，可被「清掉已失效的记录」清掉 |

两条补充：
- **改名 / 移动**：mac 上 inode 不变 → 可以反过来提示「这是刚才那个文件夹，只是改名了，要把记录指过去吗？」。
  ⚠️ Windows 上做不到就**老实不做**，别假装能认；
- ⚠️ **兜底 git 仓库问题更大**：它的 `config` 里 `bare = true`、**连工作区路径都没记**
  （实测过那份 `config`），所以连指纹都存不下 —— 要补 `git config umbra.worktree <绝对路径>` + 同一份指纹。
  **不补这个，「清掉已失效的 git 仓库」根本做不到**（目录名里的哈希不可逆）。

### 12.4 ⚠️ 这一节最该记住的

**「指纹对不上」有两种可能，而它们的处置完全不同**：

- 真的换了一个东西（删了重建）→ **不能继承**；
- 只是我们这一侧取不到那个信号（平台限制、老条目）→ **不能因此报警**。

分不清就两头错：要么静默继承（今天），要么见谁都弹窗。
所以**第三行那一档（指纹缺失 = 未知 = 不报警）和前两档一样重要**。

## 十三、M14-1 做完了：git 两条小改（2026-10-20，实测读数）

接 §11.3 那个「现成的缺口」和 §12.5 那条「兜底 git 仓库问题更大」。两样都落地了，
在 `server/src/gitkeep.ts` 一个文件里。

### 13.1 大文件闸：装在**汇流处**，不装在调用方

```
commitPaths(dir, paths, message)      ← 闸在这里
  ├── commitAfterWrite()              ← 落盘之后记一版
  ├── commitExternalChanges()         ← 发现外部改动，落盘前先存一版
  └── recordCreatedFile() 那条         ← 格式转换的成品
```

**为什么不在三个调用方各装一道**：那等于「以后再加第四条路就又漏一道」。
这和纪律① 唯一写入口是同一个形状 —— 三条路最后都收到一个函数里，闸就该在那里。

⚠️ **这条缺陷今天之前「只存在于一句注释里」**：`recordCreatedFile` 写着
「git 那一版同理不记」，而那句话**只对它自己那条路成立**（它在 `commitAfterWrite`
之前就 `return` 了）。另外三条路一道闸都没有。**注释比代码乐观，这是第二次**（§87 同族）。

**上限取和快照同一个数**（设置 → 插件沙箱 → 二进制读取上限，默认 100 MB）。
两条兜底路用两个数的话，用户会看到「版本历史里有这一版、而 git 里没有」这种
解释不了的不一致，而设置页上只写着一个数。

**跳过的只是超限那一个**，同一次提交里别的文件照常记 ——
写成「有一个超限就整次不提交」的话，一次落盘点名三个文件时另外两个的版本
会**一起丢掉**，而症状和「git 坏了」一模一样。

### 13.2 界面说得出原因：`GitFallback` 从四态变五态

`toobig` 这一档单列，**而且排在 `broken` 之前判**。理由是**出路完全不同**：

| 档 | 用户能做什么 |
| --- | --- |
| `broken` | 删掉残留的 `index.lock`，或者做完手上的 merge / rebase |
| `toobig` | **只能**去把上限调大，或者接受这个文件没有兜底 |

两个同时成立时回 `broken` 会让他去做一件**白做的事**（锁文件删掉这个文件照样不会被记进去）。

⚠️ 这一档**非说不可**：它和另三档不同 —— 不是「这个项目没兜底」，而是
「**这一个文件**我们有意没记」。不说的话用户以为它和别的文件一样有历史，
真要找回上一版时才发现没有，那时候已经晚了。

### 13.3 兜底仓库记得住「自己是谁的」

`git config` 写五项进仓库自己的 config：

```
[umbra]
    worktree  = <resolve(项目目录)>     ← 和目录名里那个哈希算的是同一个串
    dev / ino / birthtime               ← 指纹，和「打开记录」那边同一个形状（Q68）
    firstseen = <第一次见到它的时间>
```

⚠️ **为什么非记不可**：目录名是 `<目录名>__<路径 sha256 前 16 位>`，**哈希不可逆**。
591 个仓库的 `config` 里只有 `bare = true` 一行 —— 问不出它对应哪个目录，
于是「目录已经没了，把它的历史也清掉」这件事**不是没写，是写不出来**（M14-3 第②档卡在这里）。

**存量那 591 个也会补上** —— `ensureRepo` 对已经建过的仓库也调一次 `stampIdentity`，
已记过就一个子进程都不起（认 `[umbra]` 这个节名，不认 `worktree = ` 这个串 ——
后者在 `core.worktree` 上也会命中）。
⚠️ 照实说清代价：**从此再没被打开过的那些仓库，我们就是认不出来**，不猜。

⚠️ 指纹的用途要说死：**它们是用来报警的，不是用来认人的**（Q68）。
同名重建会让 `ino` 变（本机 APFS 实测 382955240 → 382955242），
而 Windows 的 file ID 官方说会复用、创建时间还会被文件系统隧道继承。

⚠️ 用 `git config` 而不是自己往 config 文件追加几行：路径里有 `#` `;` `"` 或反斜线时
git 的 config 格式要转义，**手写迟早写出一份读不回来的 config**。

### 13.4 读数

`filetest` 新增 **13 条**（都在 git 那一节里，复用同一个兜底仓库，不多造一个）。

**四道闸逐个拆、四次全红**，每次都先确认「缺陷真的落到产物里」再跑：

| 拆掉的 | 哪条判据红了 | 它红出来的读数 |
| --- | --- | --- |
| `commitPaths` 的大小闸 | 大文件没进 git | `d8bf1b0 大小混着的一次提交` ← 100 MB 真进去了 |
| `gitFallbackOf` 的 `toobig` | 界面问得出原因 | **`on`** ← 界面会**谎称有兜底** |
| `stampIdentity` | 仓库自报它是哪个目录的 | `null` |
| `ensureRepo` 给老仓库补齐那一句 | 老仓库再被打开一次就补齐了 | （红） |

两条关于判据自己的：

- **上限要现读设置，不能写死 100 MB** —— 这个数用户可以改。写死的话他把上限调大之后
  这几条判据会**在产品完全正确的情况下变红**。判据读的得和实现读的是同一个源；
- **样本用稀疏文件**（只在 `max` 那个偏移写一个字节）—— 上限可能是 1 GB，真写满又慢又占盘，
  而闸看的是 `st.size`，稀疏文件的 `size` 就是它声明的那个数。实测 `{"sz":104857601,"max":104857600}`。

⚠️ **顺带记一条仪器撒谎**：核对反向验证有没有留残留时写的是
`diff -q A B && echo "一致"` —— 这台机器上 `diff` 报了三行 `illegal option`，
**却照样走到了那句 `echo`**。一个报错的仪器给出了「通过」。
换成 `cmp` 的退出码 + `shasum` 才算量到（两边 `373414ae…` 一致）。
**判据链里任何一环报错，整条读数就都不算。**

## 十四、M14-2 做完了：身份与指纹（2026-10-20，实测读数）

落地 Q68 与 §8.5①。在 `server/src/workspace.ts` 一个文件里 + 一条接到前端的线。

### 14.1 `exists` 原来判错了东西

```
旧： existsSync(join(r.dir, "project.json"))
新： existsSync(resolve(r.dir))
```

`buildProject` **不要求** `project.json`（`readConfig(dir) ?? { name: 目录名 }`），
任意目录都能当项目打开 —— 于是「打开过一个随手的目录」这条记录**永远显示「不存在」**，
而它好好地在那儿。⚠️ 按新架构这条缺陷会**从个别变成全部**：Q62 之后我们不再往
用户目录写 `project.json`，于是**每一条**记录都会显示成不存在。

### 14.2 四档：`same` / `replaced` / `unknown` / `missing`

> ⚠️ **目标不是「鉴定」，是「不许静默继承」。** 这一句决定了全部实现。

| 档 | 什么时候 | 我们做什么 |
| --- | --- | --- |
| `same` | 指纹对得上 | 次数加一、首见时间保留 |
| `replaced` | 指纹齐、但不对 | **不继承**：次数归 1、首见重算；`open_project` 把它带回前端，界面说一句 |
| `unknown` | **指纹缺一样**（老条目 / 平台取不到） | **什么都不说**，顺手把指纹补上 |
| `missing` | 路径压根不在 | 标「已删除」，可清（M14-3） |

**`unknown` 这一档是整件事的分寸所在。** 用户机器上「最近打开」最多 20 条，
**一项指纹都没有**。把「没指纹」当成「对不上」的话，他下次打开 Studio 会收到
**二十次**「这个位置换了一个」—— 而我们其实什么都没查出来。
实测他现在那 4 条：**全部 `unknown`，会弹窗的 0 条**。

### 14.3 ⚠️ `dev` 只记不比 —— 一个有意的决定

比错的代价**不对称**：

- `dev`（设备号）**跨重启不保证稳定**（Linux 实测有变），
  而同名重建**不会**让它变；
- 所以把它算进等号里，只会在用户重启之后把一堆**本来就是它**的记录判成 `replaced`
  （白问一句，而 M14-4 之后还会**不继承** → 用户的快照历史够不着了），
  **而一个真的替换它也抓不到**。

**一个既帮不上忙、又会误伤的信号，记下来备查就好。** 进等号的是 `ino`，
`birthtimeMs` 作补强（Windows 的文件系统隧道会让同名新建继承旧创建时间 → 那时靠 `ino`；
`ino` 不可靠时靠创建时间）。

⚠️ `ino` 必须是**正数**才算量到：Windows 网络盘的 `st_ino` 不可靠、ReFS 上 64 位 ID
不唯一，Node 拿不到时给 0。**给 0 还当指纹用 = 拿一个常量认人** ——
那样全世界的目录指纹都一样，`replaced` 永远不会触发，而我们以为装了一道闸。

要给它判据得在浏览器里造一个「被替换过的目录」并从首页点进去，
而首页的项目卡来自真 STATE_ROOT —— **那就等于往用户的列表里塞东西**，不划算。

### 14.5 顺带：我自己写了一条**不可能变红**的判据

收尾自检「用户真实的「最近打开」里没有我造的任何一条」，第一版查的是
`join(process.cwd(), ".umbrastudio", "workspace.json")` ——

## 十五、M14-3 做完了：清除缓存三档（2026-10-20，实测读数）

落地 §8.7。用户原话：「**清除缓存这个功能目前应该没有，可以补充一个**」—— 实测确实没有，
只有 `purge_trash`（倒回收站里的一项）、`clear_staged_draft`、`clear_recent_projects`（**清列表不清缓存**）。

### 15.1 三件能力

| 能力 | 域 | 删什么 | 要确认吗 |
| --- | --- | --- | --- |
| `clear_project_cache`（HTTP `cache_clear`） | project | `checks/` · `shots/` · `index-data.json` · 项目根 `index-data.js` | 不要 |
| `clear_stale_records`（`records_clear_stale`） | global | 「最近打开」里 `identity: "missing"` 的那几条 + 它们的 git 兜底仓库 | 不要 |
| `forget_project`（`project_forget`） | global | 一条记录 + 它的 git 兜底历史 | **要 `confirm: true`** |

### 15.2 ⚠️ 安全线是**白名单**，不是黑名单

实现只删 `CACHE_ENTRIES` 里**点名的那几样**。写成「删 `.umbrastudio/` 下除了快照以外的东西」的话，
**以后新加一种资产就会被它删掉**，而那一天**没有任何判据会红**（判据只认得当时存在的那几种）。

`ASSET_ENTRIES`（`snapshots` · `comments.json` · `trash` · `templates` · `staged` · `chats`）
不参与实现，它只有两个用处：**给判据一人一条**，和喂那道防呆。
⚠️ 那道防呆**不是边界**（和 #24 的 `net-block.cjs` 同一个定位）——
真正的边界是白名单，它拦的是「以后有人往白名单里手抖加了一个 `snapshots`」。

⚠️ **`select-bridge.js` 和壳页面有意不在缓存名单里**：它们也是 `buildIndex` 生成的，
但删掉之后**在下一次打开之前预览和点选是坏的** ——「清一下缓存」不该让人的预览当场瞎掉。

### 15.3 「从列表去掉」和「忘掉它」是两件事，故意分成两个能力

| | `remove_recent_project` | `forget_project` |
| --- | --- | --- |
| 做什么 | 别在首页列它了 | 把我为它存的历史删掉 |
| 历史 | **一个字节都不动** | 没了 |
| 确认 | 不要 | **要** |

**把两件事做成一个按钮，等于让「整理列表」这个动作带上破坏力。**

⚠️ 这一期 `forget_project` **只删我们自己那一侧**（STATE_ROOT 的兜底仓库），
并在回执的 `stillOnDisk` 里**照实说**项目目录里那份 `.umbrastudio/` 还在 ——
今天快照 / 评论 / 回收站还在用户的目录里（M14-4 才搬过来），
而「从我的列表里忘掉这个项目」**不该有删用户目录里东西的权力**。
M14-4 之后历史全在我们这边，它才真的全删。

### 15.4 首页：失效的记录原来**静默消失**

`cap/projects.ts` 的 `describe()` 对读不出来的目录是 `catch { 跳过 }`（那是 #92 为了
「一条坏记录别拖垮整页」加的）。代价是这条记录在首页**压根不出现** ——
于是用户要的那句「文件夹不存在了，点历史记录时提示」**连『点』的机会都没有**，
他只会觉得「我上周打开过的项目不见了」。

> 顺带一个发现：`ProjectRow` **早就有 `missing` 字段**，列表视图里也早就写着
> `{p.missing ? <span className="text-err">找不到</span> : …}` ——
> **界面那一半一直在，只是数据从来没送到过。**
> 写好的分支因为上游静默吞掉而永远走不到，**而没有任何判据会红**。

现在：失效那条有一行、标「找不到」、整行半透明；**点它不去打开**（那只会得到一句
「打开项目失败」，等于什么都没说明），而是说清发生了什么和能做什么；
行尾给「忘掉它」，**点第一下只上膛**（变成「真的忘掉？」），第二下才真删 ——
形制照 `chat/History.tsx` 那条「删除不弹确认框、行内两段式」，**不新造确认弹窗**。
网格卡也补了「找不到」标：同一条记录在两种视图下说法不同，比两边都不说更糟。

设置页加了一块「存储与缓存」，两颗按钮**都不碰算不回来的东西，所以都不要确认** ——
把「清缓存」也套一层确认框，只会让人以为它危险，然后再也不点它。

⚠️ **两颗按钮打的不是同一个服务**，这一条差点写错：`clear_project_cache` 是
`scope: "project"` → 要打**项目自己那个服务**；`clear_stale_records` 是全局的 → 打 hub。
桌面壳里 **hub 不属于任何项目**，拿 hub 调项目域的能力会被门面拒掉 ——
而浏览器模式下两者恰好是同一个服务，**在浏览器里测不出来，一上桌面版就坏**
（`Ask.tsx` 头注那条「这件事在 Electron 里也成立吗」同一族）。

## 十九、B 段为什么要单独一轮：三处级联，其中一处会给出假回执

A 段做完之后我按「马上接着做 B 段」的打算又核了一遍，**核出第三处级联，而它比前两处严重**。
照实记下来，并把 B 段拆成三小段。

### 19.1 ⚠️ 第三处（新发现）：`export_project` 会**说谎**

```ts
// export.ts:64
execFile("tar", ["-czf", out, "-C", projectDir, "."], …)   // ← 只打项目目录
// export.ts:74
const snapRoot = assetDir(projectDir, "snapshots");         // ← B 段之后它指向 records/
… versionCount += …                                          // ← 数出来的版本不在包里
```

资产搬走之后：**包里一版快照都没有，而回执照样报 `versionCount: N`**。
这正是本项目反复记的那一类 —— **「假回执比没有回执糟」**（issue #35、#111 同族）。
而且它不会报错、不会白屏，用户要到**在另一台机器上导入、发现历史全没了**那一刻才知道。

`import_project` 是对称的另一半：它往目标目录解包，而历史现在不在目录里。

**所以 B 段必须同时改导出 / 导入的范围**，否则「搬迁」会变成「静默丢历史」。

### 19.2 三小段，按「有没有外部契约」排

| 段 | 做什么 | 卡在什么上 |
| --- | --- | --- |
| **B1** | ⓐ 资产（快照 / 评论 / 回收站 / 模板 / 草稿 / 会话）搬进 `records/<随机 ID>/` + **不做存量迁移**（2026-10-21 用户拍板，见 §19.4）+ **导出 / 导入跟着改** | 没有 URL 契约，但有 §19.1 那条级联 |
| **B2** | ⓑ 缓存搬进 `cache/<key>/` + `thumb` 走路由 | §17.2 ① |
| **B3** | ⓒ 壳页面与运行时改成按需 · `buildIndex` 从 `open_project` 摘掉 | §17.2 ②，**真正难的一段** |

⚠️ **B3 的难点已经看清**：`api.ts` 那句 `if (!s.indexExists) await buildIndex(…)` 的注释写着
「第一次打开：部署壳与令牌，否则 **S2 / S6 / S8 全 404**」—— 摘掉它，壳页面就得改成
**从 `TOOL_ROOT` 经路由提供**，而那几份壳自己是**稿**，里面写着 `./support.js`、
`./_ds-tool/tokens.css` 这种**相对引用**（`_ds-tool` 那一处的注释明写「拷到与设计稿里
href 相同的相对路径」）。换成路由要让这些相对引用在新的 base 下仍然解析得到。

### 19.3 ✅ 顺手定掉一件（不用拍板）：`thumb` 走路由，**设计侧零改动**

§17.2 ① 当时列了三条路。核清之后它其实不用选：

S1 索引页读的是 `index-data.json` 里的 `thumb` **值**，然后 `<img src={thumb}>`。
那个值由我们生成 —— 把它从 `.umbrastudio/shots/x.png`（相对）换成
`/__cache/shots/x.png`（**同源绝对路径**），S1 那份稿**一个字都不用改**，
因为它在项目自己那个服务下打开，绝对路径解析到同一个核心。

> **一个「要改契约」的问题，核清之后发现只是「换一个我们自己生成的值」。**
> 这种便宜要先找一遍，再去问人。

所以 B2 不需要拍板，`cacheRel()` 那个函数（A 段单列出来的那一个）就是它唯一的改动点。

### 19.4 「存量迁移」到底指什么（2026-10-21 用户问，这一节是答案）

用户的原话：「Q72 中『B1 的存量迁移』是什么意思？」

**一句话：B1 换的是「以后往哪写」，而用户机器上**已经**躺着一批写在旧位置的东西 ——
「存量迁移」就是第一次打开那个项目时，把它们从旧位置搬到新位置。
不搬的话，功能不会报错，只会**静默失忆**：历史还在盘上，而新代码去新位置找，找不到就当「没有」。

**这不是假设，是量得到的。** 2026-10-21 实测这台机器上「最近打开」的四个项目：

| 项目目录 | 旧位置里躺着什么 | 体积 |
| --- | --- | --- |
| `~/Documents/文档/UmbraStudio/test01` | `snapshots` | 22 KB |
| `projects/Umbra_design` | `snapshots` · `comments.json` · `trash` · `templates` · `staged` · `chats`（**六样全有**） | 438 KB |
| `projects/Umbra_design_next` | `snapshots` · `trash` · `templates` · `chats` | 87 KB |
| `projects/new_design` | （那六样都没有） | 20 KB |

⚠️ **注意第一行** —— 它在用户**自己的文档目录**下，不在 `projects/` 里。
这正是这一批要消除的那件事：今天我们往**任何**被打开的目录里写旁数据，
而 B1 之后它们全部住进 `STATE_ROOT/.umbrastudio/records/<key>/`。
实测 `records/` 这个目录**现在还不存在**（B1 还没做）。

**B1 的代码原本有三块，而 2026-10-21 用户把中间那块整个砍掉了。** 他的原话：

> **不用考虑就旧项目的历史记录，现在都是测试的，完全可以重新设计，历史的不用考虑，丢掉都没事。**

| 块 | 做什么 | 状态 |
| --- | --- | --- |
| ① 换写入位置 | `statedirs.ts` 的 `assetDir()` 从 `<项目>/.umbrastudio/<x>` 改成 `records/<随机 ID>/<x>` | 要做 |
| ② ~~存量迁移~~ | ~~第一次打开时把旧位置那六样拷过去~~ | 🚫 **不做**（用户拍板） |
| ③ 导出 / 导入跟着改 | `tar` 的范围（§19.1 那条假回执） | 要做，**而且是开工第一件** |

**这一刀砍掉的不只是一段代码，是 B1 里唯一一段会动用户已有数据的逻辑** ——
也就是唯一一段「写错了会丢东西」的逻辑。剩下两块都只往新位置写、只改打包范围。

⚠️ **「不用考虑」不等于「去删」。** 旧目录**留在原地、不迁也不删**，新代码只往新位置写、不去读它。三条理由：
① 纪律⑥ —— `projects/` 下的东西不是我们的，用户说「丢掉没事」是允许我们**不管**它，不是要求我们**删**它；
② 他想翻还翻得到（文件原样在盘上，上面那张表就是怎么翻的）；
③ 零代码 —— 删反而要写代码，还要写判据证明没删错别的。这也正是 Q64 原来就定下的形状。

⚠️ **副作用照实说**：那三个测试项目第一次用新版打开，版本历史 / 评论 / 会话会**看起来空了**
（其中 `Umbra_design` 那两份会话是 52 KB / 349 KB）。用户已明示这些是测试数据。

**而 Q72 也跟着定了（✅ 2026-10-21）**：`<key>` 换成**与路径无关的随机 ID**，路径只当「最后一次见到它在哪」。
原来那条「必须和迁移同一次做完，否则要迁两遍」的排期顾虑**自动消失了** —— 没有迁移，就没有迁两遍。

**key 存在哪**：`workspace.json` 的 recents 条目里多存一个 `key`。
**打开一个目录时先按指纹在 recents 里找**（M14-2 的 `ino` + `birthtimeMs` 已经量得到「这是同一个目录」，
今天只用来**拦**、没用来**认**），找到就用它记着的 key，找不到才发一个新的。
于是改名 / 移动 / 换盘都不碰历史 —— **这正是用户那条「注册表」想法用在正确那一层的样子**（`doc/11` Q46）。

### 19.4.1 ⚠️ 收尾读数要连**数法**一起写下来（2026-10-21 当场吃到）

上一轮收尾写的是「`projects/` **670 项**逐字节一致」。这一轮复核，同一个目录数出来是 **1044**。
看着像「这一轮多了 374 项」，而真相是**数法不同**：

| 怎么数 | 得到 |
| --- | --- |
| `find projects -mindepth 1`（含目录） | 1044 |
| `-type f`（只数文件） | 810 |
| `-type d`（只数目录） | 234 |
| `-mindepth 1 -not -path '*/.git/*'` | 669 |
| **`find projects -not -path '*/.git/*'`**（含 `projects` 自己、排除 `.git` 内部） | **670** ✅ |

最后那行才是上一轮用的数法，同样数法现在仍是 **670** —— **一项没多没少**。
另一条独立读数也印证：`find projects -newermt "-2 hours"` 是**空**的。

> **一个收尾读数如果没把数法写下来，它下一轮就不是读数，是一个要重新查一遍的谜。**
> 而这一次的「谜」长得正像「出事了」（374 项凭空出现），**最容易让人去改一个没坏的东西**。

以后 `projects/` 的收尾一律写成这一句，连命令带数：
`find projects -not -path '*/.git/*' | wc -l` → **670**。

#### 19.4.2 同一条命令，在不同 locale 下给不同答案（2026-10-21）

§19.4.1 记的是**数法不同**（`find projects` 含不含 `projects` 自己）。这一条更阴：**数法一样，命令一样，答案不一样。**

量「`PC 空态` 这份稿被多少处 `dc-import` 引用」，第一次得到 **128**，逐文件数出来只有 **33**。

```bash
grep -o 'dc-import name="[^"]*"' *.dc.html | sed 's/.*name="//;s/"$//' | sort | uniq -c
# 默认 locale 去重后：  6 种   ← 假
# LC_ALL=C   去重后：  16 种   ← 真
```

macOS 的 `sort` 在默认 locale 下按 collation 比中文，把 `PC 空态` / `PC 弹窗壳` / `PC 浮层菜单`
**当成同一个值**排在一起，`uniq -c` 于是把它们的计数全加到第一个上 ——
**显示出来的标签是其中任意一个，而数字是一整族的和**。

戳破它的是 `xxd -p`：把每个值转成十六进制，同一堆「看起来一样」的输出底下是 **16 种不同的字节序列**。

> **纪律④ 的一个新变种：这次不是「量到零」，是「量到一个大得正好可信的数」。**
> 128 比真值 33 大得多，但它不荒唐 —— 一份被引用上百次的基础组件完全讲得通。
> **不去对拍的话，这个数会直接进文档，而且再也不会有人怀疑它。**

**做法**：凡是对**中文或非 ASCII** 的值做 `sort` / `uniq` / `comm` / `join`，一律带 `LC_ALL=C`。
而更根本的一条是：**一个数出来之后，换一种数法再量一次** —— 两种数法对得上才算读数。

### 19.5 顺手量到的一条：原子写的 `.tmp` 没有人清（2026-10-21）

查 ① 的落点时在 `STATE_ROOT/.umbrastudio/` 下量到两个孤儿：

```
clock.json.287.tmp      0 字节    10-06 21:22
clock.json.37369.tmp   54 字节    10-02 00:21   内容是合法完整的 JSON
```

**成因确证，不是推断**：`license.ts:128` 的 `writeWatermark` 是标准的原子写
（`writeFile(tmp)` → `rename(tmp, 正式名)`），而**进程在这两步之间结束，tmp 就留下了** ——
0 字节那个是 `writeFile` 刚 open 就被打断，54 字节那个是写完了而 `rename` 没跑到

⚠️ **这不是逻辑缺陷，是这个写法的必然代价** —— 原子写买到的是「要么旧的完整要么新的完整」，
**代价就是被打断时留一个孤儿**。问题不在写法，在**没有任何人清它**：
`purge.ts` 的「清除缓存」按白名单删点名那几样，`*.tmp` 不在名单里（而白名单是对的，§十四 那条理由不变）。

**实测范围**（三处这样写）：`normalize.ts:156`（写稿那条路，**tmp 落在用户的稿旁边**）·
`license.ts:87`（许可证）· `license.ts:128`（时间水位）。
⚠️ **第一处最要紧，而实测用户的目录是干净的** —— `projects/` 三个项目加 `test01`
一个 `.tmp` 都没有（`find` 两次都是空）。写稿那条路的窗口短，被打断正好落在窗口里的概率低。
**但「概率低」不等于「不会」，而它落在用户的项目目录里就违反纪律⑥。**

| ④ | 首页右上角那颗「**导入目录**」 | 就是打开那个目录（文件就打开那个文件），**在我们的配置里记一行** | ✅ 行为已经是这样（Q62 已定）。⚠️ **但按钮名字该改** —— 见 §22.3 |

### 22.2 ①的「并存」是一个新架构，不是一个按钮

照实说量级：**现在整个前端是单项目模型**。
`App.tsx` 里 `project` 是一份全局状态，服务端那边 `serveStart` **按目录一个服务**
（issue #20 之后键是绝对路径），工作台、目录列、会话、页签全都挂在「当前这一个项目」上。

所以「一个窗口显示多个项目」要动的是：

| 层 | 要变成什么 |
| --- | --- |
| 前端状态 | `project` → `projects[]` + `activeProject`；目录列要能并排或分组 |
| 服务 | 一个窗口要同时持有**多个服务的 url + token**（现在 `Core` 一个实例对应一个项目，M14-3 刚因为这件事加了 `projectCore`） |
| 会话 | 会话是按项目存的（`records/<key>/chats/`）—— 并存时「当前会话」属于哪个项目要有明确答案 |
| 页签 | 现在页签是「项目内的文件」，并存之后页签要分两级（哪个项目 · 哪个文件） |

**〔判断〕这是一期之外的量级**，不该塞进 M14-5。
建议把 ① 先做成「**问一句，但只有『新开窗口』这一个选项**」—— 也就是先把多窗口做出来（那是 M14-5 本来就要做的），
「并存」留成单独一条（登记 `doc/12` **M15-1**）。⚠️ **这不是砍需求，是把一条真实的大改动从一条小改动里拆出来** ——
混在一起做，M14-5 会从「两天」变成「两周」，而右键打开那条路还是没通。

### 22.3 「导入」这个词在我们这儿指着两件事

| 界面上的 | 实际调的 | 做什么 | 复制文件吗 |
| --- | --- | --- | --- |
| 首页「**导入目录**」 | `open_project` | 打开那个目录，在 `workspace.json` 记一行 | ❌ 不复制（Q62） |
| 没有界面入口 | `import_project` | **解包一个 `.tar.gz` 备份**到一个空目录 | ✅ 整包落盘 |

两件事同名不同物。用户 2026-10-21 说的「导入」全部是第一件。
**建议把那颗按钮改叫「打开目录」**（或「打开…」），把「导入」这个词留给真正的解包那件。
⚠️ 这不是文案洁癖：Q47 讨论「导入要不要限白名单」时，我和用户**说的根本不是同一件能力** ——
名字撞了之后，连拍板都会拍到错的东西上。

### 22.4 导出：不限位置（Q47 已拍板）

用户原话：「用户可以任意选择位置，而且用户保存后，本地中的文件也会自动更新了，
**理论上用不到导出**，除非是想要导出其他格式，否则直接查看本地上的位置不就好了。」

两条结论：

1. **不加白名单**（Q47 结案）。已有的三道闸够了：不覆盖已存在的 · 不许落在项目里（否则 tar 会把正在写的自己打进去）· 后缀要对。
2. 「想要导出其他格式」指的是 **`file.convert`**（已有，`converttest` 42/42 钉着）——
   它和 `export_project` 是两件事：前者转一份文件的格式，后者打包整个项目。
   **用户把它们当成一件说明界面上也该分清** —— 「导出」这个词现在同时挂在两处。

### 23.4 两条产品缺陷是「顺手量到」的，不是本来要修的

1. **导出回执的 `versionCount` 翻倍**：每个快照目录里还有一份 `meta.json`，
   而它按 `.endsWith(".json")` 数 —— 3 版的项目报「6 版」。
   判据第一次跑就是「包里 3 版 · 回执说 6 版」。**和 B1 无关，本来就在说谎。**
2. **`templates.ts` 是 A 段漏掉的那一处**：A 段按「谁 import 了路径常量」收口，
   而这一处把常量**变了个形**（相对而不是绝对），于是在那次搜索里长得不像同一件事。
   后果：打开任意目录都会建出一个空的 `.umbrastudio/`。
   > A 段的注释里亲口写着「漏一处就是一类历史静默读不到」——**漏的就是它自己那一处。**

### 23.5 「打开方式」那半：Q60 的一条要照实更正

`fileAssociations` 与 `mac.extendInfo` 的 `CFBundleDocumentTypes` **是合并不是覆盖** ——
这一条 Q60 当时是读 `app-builder-lib` 的注释推的，现在有产物读数了：
`dist:dir` 出来的 `Info.plist` 里 `Folder`（`public.folder`）、`Umbra 设计稿`、`文本与数据文件` **三条都在**，
`lsregister` 也登记了对应 bindings。

⚠️ **但 `.dc.html` = Owner 这一条没验到，而且多半不成立**：
macOS LaunchServices 按**最后一段扩展名**匹配（`html`），双扩展名不是它的概念。
把 `html` 整个设成 Owner 会抢走全机器 `.html` 的默认程序 —— 那正是 Q60 把 Cursor 列为反面教材的做法。
**所以现在的实际行为是：所有类型都是 Alternate（出现在「打开方式」里，不抢默认）。**
等 sam 装包后右键一次 `.dc.html` 才能确认 LS 怎么对待那条声明。
