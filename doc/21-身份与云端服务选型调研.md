# 21 · 身份与云端服务选型调研

**这份只管选型**：用哪个开源身份框架、几个实例、几个管理后台、怎么跟版。
**不管需求** —— 账号 / 积分 / 流水 / 订单 / 商品 / 许可证要什么，在 `doc/20` §四、§五，
那份是需求出处，这份引它、不抄它。

起因：用户 2026-10-08 提了四个问题（三个项目统一框架 · 几个管理后台 ·
Casdoor 怎么升级 · 好处坏处与替代品），并明确**先出文档和计划，确认后再开工**。

⚠️ **本文所有读数都是 2026-10-08 实测**（`gh api` / `raw.githubusercontent.com` 取源码与 release），
不是凭记忆。凡标〔判断〕的是我的意见，没有读数支撑。

## 一、三个项目的现状 —— 这决定了「统一」到底是什么动作

| | UmbraStudio | Umbra（秘书本体） | inkwell |
| --- | --- | --- | --- |
| 账号 | **没有** | 〔判断〕未核（不在本仓库） | **已有自建**：`accounts`（username + `pw_hash` + `salt` + `invite_code`）+ `tokens`（会话）+ `invites`（邀请码，带 `max_uses`/`used`/`revoked`） |
| 积分 | **没接**（M11-6 明说，不画假余额） | — | **已有账本**：`account_points` + `points_ledger`（带索引）+ `INKWELL_POINTS_ENABLED` 开关 |
| 商品 / 订单 | 目录是**本地 JSON**（`plugins/catalog.json`，跟程序一起发） | — | 〔判断〕未核 |
| 管理面 | 无 | — | `INKWELL_ADMIN_TOKEN` + `invites` CLI + `review_log` / `reports` / `account_notes`（审核与举报） |
| 其它与账号绑的 | 许可证绑设备（3 台，月限 2 次解绑，`doc/20` §四） | — | `ai_usage` / `site_spend`（用量与花费）· `user_assets`（按账号存素材，200 MB/账号） |
| 栈 / 部署 | Electron + 本地 Node 核心，**离线优先** | — | Python 3.12 + React 19，**docker compose 单机**，SQLite（`runs/inkwell.db`） |

⚠️ **最要紧的一条**：inkwell **不是空地**。它已经有账号、邀请码、积分账本、审核流程、用量统计。
所以「统一到 Casdoor」对它是**迁移**，不是**接入** ——
而迁移存量密码（`pw_hash` + `salt` 自定义格式）要么对得上 Casdoor 的 `passwordType`，
要么走「强制一次重置」。**这件事的成本在 inkwell 那边，不在 UmbraStudio 这边。**

⚠️ **第二条**：UmbraStudio 的客户端是**刻意离线优先**的（许可证本地验签、目录是本地文件）。
一旦有了账号和余额，就会有「要不要联网校验」的拉扯 ——
`doc/20` §5.2 已经写死了边界：**购买必须联网，只有「用」才离线**。选型不能破坏这一条。

## 二、Casdoor 实测读数（2026-10-08）

### 2.1 基本面

| 项 | 读数 |
| --- | --- |
| 许可 | **Apache-2.0** |
| 语言 | Go（前端是它自带的 web 控制台） |
| star / 建于 / 最后推送 | **14,520** · 2020-10 · **2026-10-07** |
| 数据库 | mysql / postgres / mssql / **sqlite**（`modernc.org/sqlite`，纯 Go 无 CGO） |
| 官方部署 | `docker-compose.yml` = `casdoor` + `mysql:8.0` 两个容器；**用 sqlite 可以单容器** |
| 建表 | 启动时 xorm **`Sync2()`** 自动同步（`object/ormer.go:337` 起，`Organization` / `User` / `Application` / `Provider` / `Role`…） |

### 2.2 多租户模型 —— 这直接回答「几个后台」

```
Casdoor 实例
└── Organization（= 用户池 / 租户；有自己的 PasswordType、AccountItems、DefaultApplication）
    └── Application（= 一个 OAuth 客户端；绑一个 Organization，
                      有自己的 ClientId / ClientSecret / RedirectUris / Providers / EnableSignUp）
```

**关键性质**：登录方式（`Providers`）是**按 Application** 配的，用户池是**按 Organization** 分的。
所以「三个产品能不能共用」这件事有三种拓扑，代价不同（见 §四）。

### 2.3 身份源：32 个，国内的都在

```
alipay  dingtalk  douyin  lark  wechat  wechat_miniprogram  wechat_mobile
wecom_internal  wecom_third_party  qq  weibo  baidu  bilibili  kwai  gitee
github  gitlab  google  facebook  linkedin  twitter  telegram  okta  adfs
azuread_b2c  oidc  casdoor  infoflow_internal  infoflow_third_party
custom（通用 OAuth2）  goth（含 Apple 等一批）  provider
```

**Apple 走 `goth.go`**（见 §〇）。**这一条是 Casdoor 对我们最值钱的地方** ——
微信 / 支付宝 / Apple 这三条正是 `doc/20` §5.4 定下来的第一期三条路，**全都现成**。

### 2.4 它自带的商业化（超出我原本的预期）

`Product` 有 `IsRecharge` / `RechargeOptions` / `DisableCustomRecharge` / `Price` / `Currency` /
`Providers` / `SuccessUrl`；`User` 有 `Balance` / `BalanceCredit` / `Score`；
另有 `Order` / `Payment` / `Plan` / `Pricing` / `Subscription` / `Transaction`。

⚠️ 但要分清两件事：
- **`User.Balance` 是用户行上的一个 `float64`** —— 它是**余额**，不是账本；
- **`Transaction` 是流水**（有 `User`/`Amount`/`Category`/`Payment`/`State`）。

而 `doc/20` §5.1 要的是「**流水账本**，每一笔都要能对账，将来大模型扣费也记同一本账」。
**Casdoor 的 Transaction 能不能当那本账用，是一个要单独评估的问题**，不能想当然 ——
它的 schema 是它的，升级时跟着它走（§五）。

### 2.5 它**不做**的（这些只能我们自己写）

| 件 | 为什么它不可能有 |
| --- | --- |
| 插件目录与**上下架** | 这是我们的业务对象 |
| 插件包的**存储与分发** | 同上 |
| **Ed25519 许可证签发**（`doc/20` §4.1 离线验签的那一半） | 私钥是我们的核心资产 |
| **设备绑定**（3 台 · 月限 2 次解绑，`doc/20` §四） | 同上 |
| 审核流程（inkwell 的 `review_log` / `reports`） | 内容业务 |
| 用量与成本（`ai_usage` / `site_spend`） | 业务计量 |

⚠️ **所以「管理后台」从一开始就是两层**，不是一个东西：
**身份后台**（Casdoor 自带的控制台）和**业务后台**（插件上下架 / 积分调账 / 许可证 / 审核）。
把它们当成一个来规划，会在第一周就卡住。

## 四、三个问题的答案

### 4.1 三个项目统一用一个框架？—— 可以，但要分清统一的是哪一层

| 层 | 统一？ | 理由 |
| --- | --- | --- |
| **身份**（谁是谁、怎么登录、会话） | ✅ **统一** | 一个实例就够。这一层自己写是纯负债（`doc/20` §5.4 已经定了「不存密码、不做找回」） |
| **权益 / 账本**（积分余额、流水、订单、许可证） | ❌ **不统一进 Casdoor** | 三个产品卖的东西不一样（插件 vs 故事）；而 inkwell 已有一本账。**钱的账本是合规责任**（`doc/20` §5.3 预付值监管），不该放在一个我们不控制升级节奏的系统里 |
| **业务后台**（插件上下架 / 审核 / 调账） | ❌ **各产品一个** | UmbraStudio 的插件市场和 inkwell 的故事审核没有共同对象，塞一起只会互相拖累 |

〔判断〕**账本可以共用一份代码，但不共用一个库** —— inkwell 的 `points_ledger` 已经验证过形状，
把它抽成一个可复用的实现（而不是一个共享服务），两个产品各自跑各自的库。
这样 inkwell 不必为 UmbraStudio 的上线节奏停下来。

### 4.2 几个管理后台？

**三种拓扑，我推荐 (b)：**

| 拓扑 | 形状 | 代价 | 适合 |
| --- | --- | --- | --- |
| (a) 1 实例 · **1 Organization** · 3 Application | 一套账号登三个产品（SSO） | 用户池混在一起，将来要拆很贵；inkwell 的 UGC 合规面会牵连到 UmbraStudio | 「同一批用户、同一个品牌」 |
| **(b) 1 实例 · 2 Organization · N Application**（推荐） | **UmbraStudio + Umbra 共用一个 Organization**；**inkwell 自己一个** | 一套运维，两个用户池 | ⬅ 我们 |
| (c) 3 实例 | 完全隔离 | 运维三份、升级三次 | 真要分家时 |

**为什么 (b)**：
- UmbraStudio 和 Umbra 是**一套东西的两面**（`01` §4.8：秘书把工作台当文件面），
  而 `doc/20` §5.4 定的第一期三条路里就有「**Umbra 登录**」—— 账号互通是**产品意图**，不是巧合；
- inkwell 是面向玩家 / 作者的内容产品，用户群不同，而且它有 **UGC 审核与举报**这一套 ——
  合规面不一样的东西放一个用户池里，将来拆的成本远高于现在分开的成本。

**而业务后台：各产品一个**（见 §4.1）。所以总账是：
**1 个身份后台（Casdoor 控制台）+ 2 个业务后台（UmbraStudio 插件市场 / inkwell 内容后台）**。

### 4.3 Casdoor 怎么升级？会不会不兼容？

**实测读数**：

| 项 | 读数 |
| --- | --- |
| tag 总数 | **约 2035 个** |
| minor 节奏 | **几乎每天一个** —— v4.11.0（9-26）→ v4.18.0（10-07），11 天 8 个 |
| major 节奏 | **约 5 个月一次** —— v3.0.0（2026-04-11，从 v2.**404**.0）· v4.0.0（2026-09-01，从 v3.**164**.0） |
| 近 60 个版本里带 `BREAKING CHANGES` 的 | **只有 v4.0.0 一个** |
| v4.0.0 那条 BREAKING 是什么 | 控制台前端从 Ant Design 换成 shadcn/ui + Vite，**静态产物路径从 `build/static/{js,css}` 变成 `build/assets/`** → 「自己代理 / 自己托管它静态文件的人」会断 |
| 数据库升级 | 启动时 xorm **`Sync2()`** 自动同步：**只增不删、没有数据迁移框架、没有回退** |

**结论**：它的升级风险**不在它身上，在我们用了它多少非标准的东西**。

| 我们怎么用 | 升级代价 |
| --- | --- |
| 只用 **OIDC / OAuth2 标准面**（授权码 + 拿 id_token + 用户信息） | 几乎无痛，换成 Logto 也只改配置 |
| 用它的**管理 API**（建组织 / 查用户） | 小 —— 它的 REST 面比较稳 |
| 用它的 **Product / Payment / Transaction / Balance** | **绑上它的数据模型**，以后它改 schema 我们跟着改，而且换不掉 |
| **改它的源码** | 等于自己维护一个分支 —— **绝不做** |

**升级纪律（建议写进部署文档）**：
1. **钉死版本号**，用官方镜像，不自己 build；
2. **绝不改它的源码** —— 要定制就在我们这一侧做；
3. 升级前**备份数据库**（`Sync2` 只增不删，但没有 down migration）；
4. minor 可以跳着升，**只在 major 时读 release notes**；
5. 把我们对它的依赖**收在一个 adapter 模块里**（纪律和 `cap/` 一样：一处定义）——
   这样「换掉它」的代价是有界的，而不是散在二十处。

### 4.4 好处 / 坏处 / 有没有更合适的

**Casdoor 的好处**

| | |
| --- | --- |
| 国内三方登录全现成 | 微信（含小程序 / 移动）· 支付宝 · 钉钉 · 飞书 · 企微 · QQ · 微博…**这是自己写最贵、最容易出错的一块** |
| Apple 也有 | 走 goth，含 client secret 生成 |
| 自带管理控制台 | 身份这一层的后台不用写 |
| 商业化内置 | 充值档位 / 支付渠道（含支付宝 + 微信支付）/ 余额 / 流水 |
| Apache-2.0 | 对商业产品没有传染性 |
| 可以很轻 | sqlite + 单容器起得来 |

**Casdoor 的坏处**

| | |
| --- | --- |
| **发版极快** | 约 2035 个 tag、minor 几乎每天 —— 没有「跟版纪律」会很快失控 |
| **大而全** | 我们只要一小块（登录 + 用户），它还带着 LDAP / SAML / RADIUS / SCIM / MCP 网关 |
| **一用商业化就绑数据模型** | 见 §4.3 那张表 |
| 定制要动它的前端 | 而动了就升不动（§4.3 纪律 2） |
| 〔判断〕文档质量一般 | 我没系统读过它的文档，这条是印象，别当读数 |

**替代品里唯一真正的对手是 Logto**：MPL-2.0 · **TypeScript（和我们同语言）** ·
58 个连接器含微信 / 支付宝 / **Apple** / 钉钉 / 飞书 · 管理台现代。
**但它完全不管钱** —— 积分 / 充值 / 订单 / 支付全自己写。

## 五、建议（要你拍板）

**身份选 Casdoor，钱的账本自己写。** 理由三条：

1. **身份层是「最不该自己写」的那块**，而 Casdoor 在国内三方 + Apple 上最省事；
2. **账本是我们的核心资产与合规责任**（`doc/20` §5.3 预付值监管那条），
   不该放在一个我们不控制升级节奏的系统里；而 inkwell 已经有一本验证过的账本；
3. 这样对 Casdoor 的依赖**收窄到 OIDC 标准面 + 少量管理 API** ——
   §4.3 那张表里代价最小的一档，**换成 Logto 只改配置**。

**它的 Product / Payment 只用来做一件事：收单。**
走支付宝 / 微信支付拿到「这笔钱已付」，然后**由我们的账本记一笔积分入账**。
绑定面最小，而最贵的支付对接省掉了。

〔判断〕如果你更看重「尽快看见闭环」而不是「长期掌控」，
那就直接用它的 `Balance` + `Transaction`，少写一个账本 ——
代价是以后换不掉，而且合规问题要在它的 schema 上解。**这一条我倾向不选，但它是合理的选择。**

## 六、商城闭环现在为什么看不见（用户 2026-10-08 问的）

**不是入口没接，是目录里没有可买的东西。** 实测：

| 查的 | 读数 |
| --- | --- |
| 入口 | **项目菜单 → 「插件市场…」**（`Workbench.tsx:521`），详情区当页签打开 |
| 市场接口 | `GET /__ud/market` 正常回数据 |
| 目录内容 | `plugins/catalog.json`（2,530 字节）**只有 3 条，全部 `builtin: true` + `price: 0`** |

```
com.umbra.markdown  Markdown 编辑  价格=0  内置=true
com.umbra.code      代码与文本      价格=0  内置=true
com.umbra.html      网页预览        价格=0  内置=true
```

所以打开市场只能看到三个「随 Umbra 一起、免费、卸不掉」的插件 ——
**一个「可买」的条目都没有，闭环当然演示不出来。**

**最小闭环需要的六件**（① 不需要任何后端）：

| # | 件 | 现在 |
| --- | --- | --- |
| ① | 目录里有一条**非内置、有价格**的插件 | ❌ 没有 |
| ② | 账号 | ❌ 没有 |
| ③ | 积分余额（服务端是唯一事实） | ❌ 没有 |
| ④ | 订单（不可变，幂等键） | ❌ 没有 |
| ⑤ | 许可证签发（Ed25519） | 🚧 **客户端验的那一半已经有了**（`plugin/license.ts`），签发那一半没有 |
| ⑥ | 客户端凭许可证启用 | ✅ 已有（M11-12 授权层） |
