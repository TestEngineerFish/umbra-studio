# 25 · 一个窗口并存多个项目（M15-1）方案

> 状态：**方案稿，等拍板**（2026-10-22）。代码一行都没动。
> 来源：用户 2026-10-21 给的拖拽场景 ①「问一句：新开一个窗口，还是在当前窗口里**并存**」。
> 「新开窗口」那一半 2026-10-22 已做完（`doc/24` §24.3）；**这份只管「并存」那一半**。
> 形制交 Claude Design，这份只定**结构与取舍**。

## 〇、先更正一句：`doc/24` §22.2 那张表少说了最要紧的一件

那里列了四层（前端状态 / 服务 / 会话 / 页签），而 2026-10-22 实地量了一遍之后，
**真正决定工作量的是第五件，它不在那张表上**：

```
app/src/App.tsx:179
  <Workbench key={project.dir} project={project} … />
                ^^^^^^^^^^^^^^^^^
```

**切项目的时候整个工作台是「重挂」的。** 也就是说 `Workbench.tsx` 里那
**32 处 `project.dir`** 之所以今天不出错，**不是因为它们被小心写过**，
是因为它们**每次只活在一个项目里** —— 组件生命周期替我们维持住了那个不变量。

> **「单项目」不是一个被写进代码里的假设，是一个被 `key=` 替我们维持住的不变量。**

并存的全部意义是**两个项目同时活着**，所以这个 `key` 必须拿掉；
而拿掉的那一刻，那 32 处同时变成可疑点，**编译器一个都不会报**
（它们的类型没变，只是「当前是哪个」这件事不再由挂载决定了）。

这正是 M14-5 下半那个「`mainWin` 单例被九处读着」的同一种形状，**而这次是 32 处**。
⚠️ 所以下面 §三 的第一条不是「加一层状态」，是「**把那个不变量换成一个显式的、编译器管得到的东西**」。

## 一、量到的现状（2026-10-22，不是推断）

| 层 | 现在是什么 | 读数 |
| --- | --- | --- |
| 前端状态 | `App.tsx` 一份 `project: ProjectHandle \| null` | 读取点：`Workbench.tsx` **32** · `App.tsx` 4 · `kinds/toolbar.tsx` 2 · `kinds/fallback.tsx` 1 |
| 工作台 | `key={project.dir}` → **切项目整体重挂** | 1 处，而它是上面 32 处的前提 |
| HTTP 客户端 | `Core` 一个实例对应一个项目（`useMemo` on `project`） | `Workbench.tsx:121` · `App.tsx:34`（M14-3 加的 `projectCore`） |
| 服务 | `serveStart` **按绝对目录**去重（issue #20），一个目录一台 | `serveStop(dir)` 函数**有**；**HTTP / MCP 面没有任何停服务的能力** |
| 会话 | 服务端按项目存：`records/<ID>/chats/`；前端 `useChat(core, dir, …)` | 1 处入口 |
| 页签 | `us.tabs.<项目目录>` 存在浏览器 `mem` 里，内容是**项目内的相对路径** | 以项目目录为键的 mem 还有 `us.lastDraft.<dir>` · `us.kind.<…>` · `us.viewByDir` |
| 窗口 | **多窗口已经有了**（2026-10-22，`shell/main.mjs` 的 `wins` 集合） | `shelltest` 钉着「两个窗口互不串线」 |

⚠️ **「HTTP 面没有停服务的能力」这一条要留意**：它是 `doc/00` §166 那次
「`uitest` 一台机器攒了 33 个 LISTEN」的根因之一。并存会让**一个窗口同时开 N 台服务**，
而关掉其中一个项目时**现在没有任何办法把那一台停掉** —— 见 §四 取舍 D。

## 二、不做什么（先划掉，免得越做越大）

| 不做 | 为什么 |
| --- | --- |
| **跨项目搜索 / 跨项目引用** | Q78：「**我们不是全局的 IDE，只是针对文件的编辑器**」。并存是「同屏看两个项目」，不是「把两个项目合成一个」 |
| **跨项目拖文件** | 它等于 `copy_into_project` 的另一个入口，而那一件已经有了。并存第一期不给它，省掉「拖到另一个项目的树里」这整套落点判定 |
| **一个会话同时看两个项目** | 会话是按项目存的（`records/<ID>/chats/`），一个会话属于两个项目的话「这条历史存哪」没有答案。见取舍 B |
| **分屏并排看两个项目的详情区** | 那是「多栏布局」，和「并存多个项目」是两件事。第一期只并存**导航与会话的归属**，详情区一次仍然只显示一份文件 |

> **并存要先回答「当前是哪个项目」，而不是先回答「能不能同时看两个」。**
> 前者是结构，后者是布局 —— 布局那件可以在结构做对之后单独排。

## 三、结构：四件事 + 那个不变量

### 3.1 把 `key=` 换成一个编译器管得到的东西（**先做这一件**）

`Workbench` 不再按 `project.dir` 重挂，所以「当前是哪个项目」必须变成一个**显式的值**。
做法不是「加个 `activeProject` 变量然后到处读它」—— 那只是把 32 处隐式依赖
换成 32 处显式依赖，**漏一处照样静默**。

**做法：把那 32 处依赖收成一个 `useActiveProject()`，并让「拿错项目」在类型上不成立。**

```ts
/** 一个窗口里并存的那几个项目。 */
interface WindowProjects {
  list: ProjectEntry[];          // 顺序 = 界面上的顺序
  activeDir: string;             // 当前是哪一个
}
/** 一个项目在这个窗口里的全部东西 —— **它自带 core**，而不是让调用方自己 new */
interface ProjectEntry {
  handle: ProjectHandle;         // url / token / ws / dir / designProject / editable
  core: Core;                    // 一个项目一个，窗口持有，切项目不重建
}
```

⚠️ **关键一步**：`Workbench` 的 props 从 `project: ProjectHandle` 换成
`active: ProjectEntry`，**而 `core` 从 props 进来、不再在 Workbench 里 `useMemo`**。
这样「这个 `core` 是哪个项目的」和「这个 `project` 是哪个项目的」**是同一个对象的两半**，
拿错一半在类型上就拼不起来。

> 现在的写法里 `core` 和 `project` 是两个独立的值（`core = useMemo(…, [project])`），
> 并存之后**它们可以不一致**，而那种不一致的症状是
> **「改动落在另一个项目的文件上，而界面一句话都不说」** —— issue #20 那一条的重演。
> 把它们绑成一个对象，是把那个 bug 变成编译错误。

⚠️ **以项目目录为键的 mem（`us.tabs.<dir>` / `us.lastDraft.<dir>` / `us.kind.`）照旧** ——
它们本来就带着目录，并存之后**恰好不用改**。这是现状里唯一一处已经做对了的。

### 3.2 一个窗口持有多份 url / token

`Core` 一个项目一个实例（已经是这样），变的只是**谁持有它们**：
从「`Workbench` 自己 `useMemo` 一个」变成「窗口持有一张 `dir → ProjectEntry` 的表」。

⚠️ **WebSocket 要点一下**：每个 `Core` 自己连一条 WS（`project.ws`）。
并存 N 个项目 = N 条 WS + N 台 HTTP 服务。**这是真实成本，不是「反正都在本机」**：
`doc/00` §166 实测一台机器攒过 **33 个 LISTEN**。所以取舍 D 要定上限。

### 3.3 会话归属

会话按项目存在 `records/<ID>/chats/`，这一层**不用改**。
要定的是界面上「当前会话」属于谁 —— 见取舍 B。

### 3.4 两级页签

现在页签是「项目内的文件」，`us.tabs.<dir>` 一个项目一串。
并存之后**两级的那一级在哪**是形制问题（交 Claude Design），
但**数据结构有两种，而它们不等价** —— 见取舍 A。

## 四、要你拍板的取舍

### A. 两级页签的结构：是「每个项目一串页签」还是「一串页签带项目标记」

| | A1 一个项目一串（推荐） | A2 一串混排，每个页签标项目 |
| --- | --- | --- |
| 数据 | `us.tabs.<dir>` **照旧**，一个项目一串 | 要新建一份跨项目的页签表，`us.tabs.<dir>` 变成历史 |
| 切项目 | 页签条整条换掉 | 页签条不变，当前项目随选中的页签变 |
| 「我刚才在另一个项目看的那份文件」 | 切回去还在（每个项目记着自己的） | 一直在条上，不用切 |
| 页签条会不会爆 | 不会（一次只显示一个项目的） | **会** —— 两个项目各开 8 个页签就是 16 个 |
| 存量 | **零迁移** | 要迁 `us.tabs.<dir>`，而那是用户已经有的状态 |
| 实现量 | 小（页签那一层几乎不用动） | 中（`Tab` 要带项目、`TabBar` 的所有动作要带项目、`normalize()` 要认两种存量） |

**我推荐 A1**，三条理由，第三条是决定性的：
① 页签条不会爆；② `us.tabs.<dir>` 零迁移；
③ **A2 把「当前是哪个项目」变成了「当前选中哪个页签」的副产品** ——
而那意味着「关掉最后一个页签」= 「这个项目还在不在窗口里」没有答案。
A1 里项目是一等的东西，页签是它下面的东西，**层级和数据结构一致**。

⚠️ A1 需要形制上有一个**项目切换器**（Claude Design 定长什么样：
左边一列项目？页签条上面一条项目条？项目名菜单里列出来？）。

### B. 关掉一个项目时，它那条正在跑的 AI 会话怎么办

会话是**异步作业**（轮询最长 12 分钟，`doc/00` §117 那一族），所以这件事必须有答案。

| | B1 拦一句（推荐） | B2 后台继续跑 | B3 直接中断 |
| --- | --- | --- | --- |
| 行为 | 有一轮在跑 → 问「这一轮还在跑，关掉就看不到结果了」 | 关掉项目但作业照跑，跑完落盘 | 关掉即 `chat_abort` |
| 用户能看到结果吗 | 他自己决定 | 看不到（界面没了），但文件改了 | 看不到，文件也没改 |
| 风险 | 多一次确认 | **文件被改了而他没看到变更卡** —— 这是「假成功」的一种 | 他可能刚好不想中断 |

**我推荐 B1**，理由：这个窗口里的会话**能写他的文件**，而 B2 的后果是
**改动落了盘而「变更卡 + 一键回退」那一屏他从来没见过** —— 那正是 §19.1 那一族的假回执。
⚠️ 而且 B1 **有现成的东西可用**：`guardUnsaved()` / `LeaveGuard` 已经在做「有没落盘就拦一句」，
这里是同一个形制、同一个位置，**不新造一种**。

### C. 一个窗口里最多并存几个项目

| | C1 上限 4（推荐） | C2 不限 |
| --- | --- | --- |
| 成本 | 4 台 HTTP + 4 条 WS + 4 份目录树 | 没有上限 |
| 到上限之后 | 再拖进来 → 那一问里「并存」那档变灰 + 说「这个窗口最多 4 个，可以开新窗口」 | — |

**我推荐 C1 = 4**，而理由是**可以量的**：`doc/00` §166 实测一台机器攒过 33 个 LISTEN，
而那只是回归留下的。并存没有上限的话，**用户自己就能把它堆到那个量级**，
而每台服务都带一份文件监听 + 一条 WS。
⚠️ 4 这个数我**没有量过**（没有「几个项目开始卡」的读数），所以它是一个**保守的起点**，
不是一个测出来的结论 —— 照实说。要定别的数也行，我只建议**有一个上限**。

### D. 关掉一个项目要不要把它那台服务停掉

⚠️ **这一条是现状里的一个真空**：`serveStop(dir)` 函数有，但 **HTTP / MCP 面一件能力都没有**
（grep 过 14 个 `cap/*.ts`，零命中）。并存之后「关掉一个项目」第一次有了真实的调用方。

| | D1 加一件 `close_project`（推荐） | D2 不停，留着 |
| --- | --- | --- |
| 行为 | 关项目 → 停那台服务、断那条 WS | 服务一直活到进程退出 |
| 后果 | 再打开同一个项目要重启一台（几十毫秒） | **N 个窗口 × N 个项目的服务只增不减** —— §166 那条的产品版 |
| 风险 | ⚠️ **同一台服务可能被另一个窗口用着**（`serveStart` 按目录去重，两个窗口打开同一个项目**共用一台**）→ 停错了会把另一个窗口弄瘫 |

**我推荐 D1，但必须带引用计数** —— 而这正是 D1 唯一的实现难点：
`running` 那张表现在只记「这个目录有一台服务」，不记「有几个窗口在用它」。
> **「按目录去重」和「按目录停掉」是一对**：有了前者就必须有后者的引用计数，
> 否则「去重」会让一个窗口的关闭动作影响另一个窗口 —— 而那是 issue #20 的反向重演。

⚠️ 如果你选 D2，那至少要有一条判据钉住「服务数不随开关项目增长」，
不然它会变成下一个 §166。

### E. 「并存」这一档在那个问句里怎么说

现在那一问是两档（`doc/24` §24.3）：

```
怎么打开它？
  [取消 Esc]  [在新窗口里打开]  [在当前窗口打开]
```

并存做完之后第三档加在哪：

| | E1 替掉「在当前窗口打开」（推荐） | E2 三档并列 |
| --- | --- | --- |
| 字面 | `[取消] [在新窗口里打开] [加到这个窗口]` | `[取消] [新窗口] [加到这个窗口] [在当前窗口打开]` |
| 「在当前窗口打开」去哪了 | 没了 —— 并存之后它的意思变成「**关掉当前项目再开这个**」，而那件事用户可以关掉项目再打开 | 留着 |

**我推荐 E1**：并存之后「在当前窗口打开」这句话**本身变得不准确** ——
它实际做的是「离开当前项目」，而那是一个**破坏性动作**（当前项目的页签、会话视图都没了），
不该和「加到这个窗口」这种无损动作并列在同一行按钮里。
⚠️ 字面交 Claude Design，我只建议**三档里不要有两档听起来像同一件事**。

## 五、分段做（每段自己能跑、自己有读数）

| 段 | 做什么 | 判据落在哪 | 风险 |
| --- | --- | --- | --- |
| **S1** | 把 `core` 和 `handle` 绑成 `ProjectEntry`，`Workbench` 收 `active: ProjectEntry`，**`key=` 先留着** | 现有全套回归**一条不变**（零行为变化，和 M14-4 A 段同一个做法） | 低 |
| **S2** | 窗口持有 `list[] + activeDir`，**拿掉 `key=`**，加项目切换器 | 新建 `app/multiprojtest.mjs`（真开浏览器 + 临时 `STATE_ROOT`）：两个项目同时在、切换之后**页签 / 详情 / 会话各自是自己的**、**改动落在正确的项目上** | **高** —— 那 32 处在这一段现形 |
| **S3** | 关项目：B1 那一问 + D1 的 `close_project` + 引用计数 | 判据：两个窗口开同一个项目 → 关掉一个，**另一个还活着**；关完服务数回落 | 中 |
| **S4** | 拖拽那一问加第三档（E1） | `hometest` ⑦ 加一条 | 低 |

⚠️ **S2 要有一条「改动落在正确的项目上」的端到端判据，而且它是这一整件事的验收点。**
理由：那 32 处里任何一处拿错项目，症状都是
**「改动落在另一个项目的文件上，而界面一句话都不说」** ——
DOM 判据说不出这件事（界面看起来完全正常），**只有去盘上数才看得见**。
> **一条端到端的判据顶十条关于状态形状的判据**（`00` §172.7 原话）。
